# 02 分块策略与重叠窗口：chunk_size 到底怎么选

> 对应技能：检索与知识库 ｜ 状态：已跑对照实验（真实数据）

## 1. 背景与目标

文档入库前必须切块。块太大，一个向量混多个主题、相似度被拉平；块太小，答案横跨边界被切断。目标是用实验而不是直觉回答：chunk_size 取多少、overlap 取多少，为什么。

## 2. 环境与依赖

- 复用 `ingest.py`，通过 `--chunk-size` / `--overlap` 命令行覆盖参数
- `experiment.py` 的 A-F 组专门测分块变量
- 评测集 `eval_set.json` 30 题，每题标注正确来源文档

## 3. 核心实现

分块逻辑（`ingest.py`）：

```python
def chunk_text(text, chunk_size, overlap):
    step = max(1, chunk_size - overlap)          # 滑动步长
    chunks = []
    for i in range(0, len(text), step):
        part = text[i:i + chunk_size].strip()
        if len(part) >= max(20, chunk_size // 4):  # 丢掉过短的尾块
            chunks.append(part)
        if i + chunk_size >= len(text):
            break
    return chunks
```

每块生成稳定 ID `文件名#序号`，带来源元数据——这是回答能追溯的前提。

## 4. 关键参数与踩坑

- overlap 是块大小的 10%~20% 作起点；本例 100/500=20%。
- **overlap 不是越大越好**：重叠过大让重复内容挤占 Top-k 名额。
- 切块要保留结构信息（标题、来源文件名拼进块首），否则回答给不出可核查来源。
- 中文语料块偏小、英文偏大；没有语义切分工具时，固定长度+重叠也能跑通。

## 5. 结果验证

14 组实验里 A-F 组（其余参数固定为 k=4、混合+重排）：

| 组 | 变量 | 块数 | 命中率 | 平均延迟 |
|---|---|---:|---:|---:|
| A | chunk_size=300 | 48 | 96.67% | 0.0098s |
| **B** | **chunk_size=500（基线）** | 26 | **100.00%** | 0.0079s |
| C | chunk_size=1000 | 12 | 100.00% | 0.0062s |
| D | overlap=0 | 21 | 96.67% | 0.0127s |
| **E** | **overlap=100（基线）** | 26 | 100.00% | 0.0143s |
| F | overlap=200 | 32 | 93.33% | 0.0091s |

**结论**：小语料上 chunk 500/1000 打平，1000 块数更少、延迟更低；overlap=200 命中率反降到 93.33%，重复内容占位是主因。详见 `evidence/experiment_results.md`。

## 6. 面试怎么讲

"我用对照实验选分块参数，固定 k 和检索方式只改一个变量。chunk_size 从 300/500/1000 扫了一遍，重叠窗口从 0/100/200 扫了一遍。发现 overlap 过大反而掉点，因为重复块挤占 Top-k。最终在小语料上选 500/100 作基线，但我会说明样本只有 5 篇文档，结论需要更大语料验证——不把小样本结果吹成通用最优。"

> 局限：延迟数据受本机状态影响，只能看同环境相对值。
