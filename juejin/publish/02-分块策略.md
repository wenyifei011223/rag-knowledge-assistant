文档入库前必须切块。块太大，一个向量混多个主题、相似度被拉平；块太小，答案横跨边界被切断。这是 RAG 调参的第一个坑，也是最容易被"默认值"糊弄过去的坑。

这篇用对照实验而不是直觉回答：chunk_size 取多少、overlap 取多少，为什么。

## 一、实验设置：固定其他变量，只改一个

复用 `ingest.py`，通过 `--chunk-size` / `--overlap` 命令行覆盖参数；用 `experiment.py` 的 A-F 组专门测分块变量；评测集 `eval_set.json` 有 30 题，每题标注正确来源文档。

命中率定义：Top-k 结果里包含该题标注的正确来源文档即命中，命中率 = 命中数 / 30。除了被测变量，其余参数固定为 `k=4、混合检索+重排`。

## 二、分块逻辑：滑动窗口 + 稳定 ID

```python
def chunk_text(text, chunk_size, overlap):
    step = max(1, chunk_size - overlap)          # 滑动步长
    chunks = []
    for i in range(0, len(text), step):
        part = text[i:i + chunk_size].strip()
        if len(part) >= max(20, chunk_size // 4):  # 丢掉过短的尾块
            chunks.append(part)
        if i + chunk_size >= len(text):
            break
    return chunks
```

每块生成稳定 ID（`文件名#序号`），带来源元数据。切块时把标题、来源文件名拼进块首，否则回答给不出可核查来源。

## 三、踩坑：overlap 不是越大越好

- overlap 一般取块大小的 10%~20% 作起点，本例 `100/500 = 20%`。
- **重叠过大会掉点**：重复内容挤占 Top-k 名额，把真正相关的块挤出去了。
- 中文语料块偏小、英文偏大；没有语义切分工具时，固定长度 + 重叠也能跑通。

## 四、结果：A-F 组真实数据

| 组 | 变量 | 块数 | 命中率 | 平均延迟 |
|---|---|---:|---:|---:|
| A | chunk_size=300 | 48 | 96.67% | 0.0098s |
| **B** | **chunk_size=500（基线）** | 26 | **100.00%** | 0.0079s |
| C | chunk_size=1000 | 12 | 100.00% | 0.0062s |
| D | overlap=0 | 21 | 96.67% | 0.0127s |
| **E** | **overlap=100（基线）** | 26 | 100.00% | 0.0143s |
| F | overlap=200 | 32 | 93.33% | 0.0091s |

**结论**：

- 小语料上 chunk 500 和 1000 打平，但 1000 块数更少、延迟更低。
- `overlap=200` 命中率反降到 93.33%，重复内容占位是主因——这就是"越大越好"直觉的失败案例。
- `overlap=0` 也掉到 96.67%，说明边界切断确实丢了答案。

## 五、必须说清的局限

样本只有 5 篇文档、30 道题，基线命中率偏高（100%）不代表真实业务效果。延迟数据受本机状态影响，只能看同环境相对值。这组数字的意义在于**展示调参方法**，而不是宣布"500/100 是通用最优"。

如果语料换成真实业务文档，正确做法是把这套实验脚本搬过去重跑，用自己的评测集重新选参数。

## 结语

分块没有万能参数，只有"在你的评测集上跑出来的参数"。把 `chunk_size`、`overlap` 暴露成命令行参数，写个脚本扫一遍，比记任何经验值都靠谱。
