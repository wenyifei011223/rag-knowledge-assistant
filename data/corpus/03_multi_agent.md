# 多智能体系统设计：工具、状态与服务化

单个 Agent 能做的事有上限：工具一多，提示词变长，模型选择工具的正确率下降；流程一复杂，一个分支失败就拖垮整条链。把职责拆给多个 Agent，每个 Agent 只面对少量工具和短提示词，是可维护性的关键。

## 工具定义与参数校验

工具是 Agent 能调用的外部能力，本质是"函数 + 描述 + 参数 Schema"。用 Pydantic 定义 args_schema 后，框架会自动把类型注解转成 JSON Schema 交给模型；模型给出的参数在执行前会经过校验，类型不对或必填缺失会在调用工具函数之前被拦下，而不是在运行中抛异常。

参数校验的意义不只是防错，更是给模型清晰的调用契约。描述写得含糊，模型就会猜参数；Schema 写得明确，模型就知道该传什么。工具名也要稳定且有区分度，两个名字相近的工具会让模型反复选错。

工具执行必备三件套：参数校验、有限重试、异常兜底。重试要设上限（例如 2 次）并配合指数退避，避免网络抖动时无限循环。超过上限后返回可读的错误信息而不是堆栈，让 Agent 能把这个错误当作观察结果，决定换工具或终止。

## ReAct 闭环与手写字 StateGraph

ReAct 的模式是思考-行动-观察循环：模型先输出一步推理和要调用的工具，框架执行工具并返回观察，模型再基于观察决定下一步。循环终止条件是没有工具调用请求时走到结束节点。

用状态图手写这个循环，结构比抽象封装更清晰。典型节点包括模型节点和工具节点。模型节点调用大模型，产出可能带 tool_calls 的消息；条件边检查消息里有没有 tool_calls，有就把控制权交给工具节点，没有就直接走到 END。工具节点执行完所有调用，把结果作为新消息追加回状态，再回到模型节点。

这种写法的调试优势很明显：每个节点输入输出都是显式状态，可以在任意节点打断点，看模型到底是因为工具描述不清选错了，还是观察结果格式不对导致后续推理跑偏。

## 规划、检索、汇总三类 Agent 的职责分离

把一个问答流程拆成三个角色，每个角色只做一件事。规划 Agent 拆解问题，决定需要查什么、按什么顺序查，输出一份简明计划。检索 Agent 拿计划执行工具调用，只负责拿到证据，不对答案下结论。汇总 Agent 拿证据组织成带引用的回答，不重新检索。

状态在节点间流转，典型字段包括原始问题 question、规划结果 plan、证据列表 evidence 和最终回答 answer。每个节点只读自己需要的字段、写自己负责的字段，状态传递路径清晰，出问题时容易定位是哪一步污染了数据。

拆分还有测试价值：每个 Agent 可以单独用固定输入测输出，不必每次都跑端到端。检索 Agent 可以用不需要大模型的假计划直接测工具调用成功率；汇总 Agent 可以用固定证据测引用是否准确。

## 长对话的上下文控制

多轮对话把历史全塞进提示词，token 会随轮次线性增长，最终触发上限或让模型忽略早期信息。常见策略有两种。一是窗口截断，只保留最近 N 轮，简单但会丢掉关键背景。二是摘要压缩：当历史超过阈值时，用大模型把早期对话压成一段摘要，后续只带摘要加最近几轮。

状态持久化用 checkpointer，按 thread_id 保存每个会话的状态。这样同一个会话在不同进程、不同时间点都能恢复到最近的上下文，也便于做会话级别的评测和回放。

## FastAPI 服务化

把链路封成服务，最小接口两个：/ask 接收问题和会话标识，返回回答与引用；/health 返回服务状态，用于容器健康检查。用 Pydantic 模型定义请求和响应体，接口参数自动有类型校验和文档。启动用 uvicorn，访问 /docs 能看到自动生成的 Swagger 页面，方便手工验证和截图留证。

服务层要把链路的中间量也返回给调用方，至少包括检索方式、引用来源和耗时。这些字段既方便前端展示依据，也方便线上排查"回答为什么这么来"。

错误要在服务层统一处理：工具失败、模型超时、检索为空都返回结构化错误码，不要直接把异常抛给客户端。

## Docker 部署

写 Dockerfile 构建镜像时，注意把依赖安装和代码复制分成两层，先复制 requirements.txt 安装依赖，再复制代码，这样代码变动时可以利用构建缓存。暴露服务端口，用 docker run 做端口映射启动。

容器里必须能访问到语料和索引文件，要么打进镜像，要么通过数据卷挂载。前者适合只读的固定知识库，后者适合索引会更新的场景。健康检查用 /health 接口，配合重启策略可以在服务异常时自动恢复。

部署完成后至少验证三件事：/health 返回正常、/ask 能对域内问题返回带引用的回答、对域外问题返回拒答。三项都通过才算链路真正跑通。
