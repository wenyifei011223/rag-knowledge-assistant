# 零依赖跑通一个 RAG 基线：从文档分块到带引用的回答

很多人学 RAG 的顺序是：先看概念，再装 LangChain，再接 Chroma，最后接大模型。链路一长，出问题就不知道是哪一环坏了：是分块切丢了上下文？是向量检索没召回？还是提示词没约束住模型？

我换了个顺序：先用纯 Python 标准库把每条链路跑通，每一环都留下可检查的输出，再逐个替换成正式组件。这篇文章记录这个基线的完整实现思路。

## 一、先把链路拆开

RAG 拆成离线和在线两段：

- **离线**：加载文档 → 清洗 → 分块 → 计算向量 → 写入索引
- **在线**：问题改写 → 检索 → 重排 → 组装上下文 → 生成带引用的回答

拆开的好处是每段都能单独测。离线段出了问题时，向量库里有什么一查就知道；在线段出了问题，可以把中间量打印出来定位。

## 二、离线段：分块比模型更影响结果

分块代码核心只有十几行：

```python
def chunk_text(text, chunk_size, overlap):
    step = max(1, chunk_size - overlap)
    chunks = []
    for i in range(0, len(text), step):
        part = text[i:i + chunk_size].strip()
        if len(part) >= max(20, chunk_size // 4):
            chunks.append(part)
        if i + chunk_size >= len(text):
            break
    return chunks
```

`chunk_size=500, overlap=100` 是常见的起点，但它不是结论。块太大，一个向量里混了多个主题，相似度被拉平；块太小，答案横跨两块就被切断。重叠窗口能缓解边界问题，但代价是块数增加，同一段内容在 Top-k 里重复占位。

每块要带上来源文件名和序号，拼成稳定 ID，比如 `02_rag_pipeline.md#003`。没有这个 ID，回答里的"引用"就是空话。

向量化默认用 TF-IDF：建词表、算 tf-idf、L2 归一化。它不懂语义，但零依赖、可复现，适合先把链路跑通。代码里留了自动切换：检测到 `sentence-transformers` 就用 bge 替换。

## 三、在线段：混合检索为什么有效

稠密向量擅长语义匹配，"怎么让机器人查资料"能召回"检索增强生成的原理"；但它对精确代号不稳定，产品型号、错误码这类词在训练语料里可能几乎没出现过。

BM25 正好相反：它不理解语义，但对精确词项极其敏感。于是把两路结果融合：

```python
def rrf_fuse(dense, bm25, top_k):
    fused = {}
    for rank, item in enumerate(dense, 1):
        fused.setdefault(item["id"], {**item, "score": 0.0})["score"] += 1 / (60 + rank)
    for rank, item in enumerate(bm25, 1):
        fused.setdefault(item["id"], {**item, "score": 0.0})["score"] += 1 / (60 + rank)
    return sorted(fused.values(), key=lambda x: x["score"], reverse=True)[:top_k]
```

RRF 的巧妙之处是不用归一化两路的分数，只看名次。某文档在第 r 名出现就贡献 `1/(60+r)`。这样不同量纲的分数可以直接相加，某一路的异常高分也不会主导结果。

重排放在候选集上做：先召回 20-50 个候选，再用 cross-encoder 精排到 Top-3~Top-8。因为 cross-encoder 把查询和段落拼在一起联合编码，精度高但无法预计算文档向量，全库做会慢到不可用。没有 cross-encoder 时，可以用词项覆盖率降级，但要在输出里标明用的是降级方案。

## 四、幻觉抑制不是一句提示词

提示词只有三条硬约束：只用上下文、每个结论标来源、没有依据就说"未找到相关依据"。

但光靠提示词不够。域外问题如果检索出一堆无关段落塞进上下文，模型反而更容易顺着编。所以加一道检索侧防线：过滤掉"怎么""什么"这类通用疑问词后，检查查询的领域词是否与召回内容有实质重合，没有就拒答。

有个细节很关键：中文不能只按单字切词。"今天天气怎么样"和"怎么保证回答不编造"共享"怎么""怎么样"，单字重合率很高。改用二元组并过滤掉通用二元组后，域外判定才稳定。

多轮对话的追问也要处理。"它为什么这么做"单独检索几乎没有信息量，要用历史把它改写成独立问题。有大模型就用提示词改写，没有就用规则降级——把最近两轮历史拼上来，虽然啰嗦但至少带上领域词。

## 五、验证：14 组对照实验

链路跑通不等于参数合理。我固定评测集，一次只改一个变量，跑了 14 组实验。基线是 chunk_size=500、overlap=100、k=4、混合检索加重排。

几个真实结论：

- **k=2 命中率掉到 86.67%，基线是 100%**：召回数量不足是最稳定的负面影响。
- **overlap=200 反而降到 93.33%**：重叠过大让重复内容挤占 Top-k 名额。
- **纯向量延迟最低（0.0024s vs 基线 0.0079s），但少命中一题**：混合检索的价值要在精确标识符类问题上才明显，当前评测集这类题不够多。
- **多数组别持平在 100%**：这暴露了问题——语料只有 5 篇、评测题围绕这些文档设计，区分度不足。

最后这条最重要。很多人晒出 95%+ 的命中率就收工，但这个数字如果来自小语料和自造评测集，说明不了什么。**我把局限写进 README，而不是藏起来**：需要更大更真实的语料才能选出有说服力的参数。

## 六、这套基线能拿去做什么

它的价值不是"效果多好"，而是：

1. 换一台机器，一条命令能复现全部产物；
2. 每一环都有中间输出，出问题能定位；
3. 实验数字来自真实运行，且标明了语料规模和降级情况；
4. 装好依赖、配上 Key 后能自动升级到正式配置，重跑即可对比。

工程上，一个能复现、能解释、能升级的基线，比一个跑出漂亮数字但说不清来源的 demo 有用得多。
